# План рефакторинга Wordsapp

## Цель и согласованные решения

Привести всё мобильное приложение к правилам `AGENTS.md` и согласованной архитектуре обработки данных. Снизить связанность изменений, выделить проверяемые бизнес-правила и сохранить существующие пользовательские сценарии. Выполнять работу последовательными законченными этапами в ветке `codex/app-architecture-refactor`.

Согласовано с пользователем:

- Список доступных типов упражнений остаётся справочником в коде.
- `words service` отвечает за данные слов, `progress service` — за прогресс, `training service` — за подбор материала и доступных упражнений.
- `training pool` содержит типы упражнений текущей сессии. Mixed выбирает случайное упражнение из оставшихся; при 100% оно исключается. Одиночная тренировка использует тот же механизм с одним элементом.
- `words pool` хранит данные для упражнений. Данные слов и выборка/очередь должны иметь определённых владельцев.
- Training manager остаётся React-хуком интеграции. Контекст сохраняет роль событий приложения и обратной связи; не требуется менять событийную модель ради новой структуры.
- Сервисы и чистые правила отделены от React, навигации и представления.
- Полный охват приложения означает обработку всех текущих подсистем, а не обязательное переписывание каждого компонента или перенос всего в `src/`.

## Ограничения совместимости

- Не обновлять SDK, React, React Native, библиотеки состояния, UI-kit или assistant runtime.
- Не менять дизайн, локализации, доступность, маршруты, URL-параметры, deep links и серверные контракты без необходимости для согласованного изменения.
- Сохранить схему WatermelonDB версии 9, имена таблиц, SecureStore keys, файл `has_launched`, ключи пользовательских настроек и сериализованный формат dialogue cache.
- Сохранить существующие score increments, сброс score при ошибке, `intro`, ограничение mixed до 20 слов и приоритет слов диалога.
- Для завершения упражнений сохранить текущую семантику покрытия: `score > 0` для пары слово–тип упражнения. Это не среднее значение score и не требование score = 1.
- Не включать новые автоматические отправки прогресса на сервер как побочный эффект: `useLearningSync` существует, но его вызовы в приложении при исходном аудите не найдены. Документировать фактический статус, извлечь код при необходимости; не выдавать его за работающий outbox.
- Не менять пользовательский `AGENTS.md`. Включить его исходное содержимое в ветку вместе с выполнением правил.
- Не использовать `any`, `ts-ignore`, отключение проверок или фиктивные успешные результаты для прохождения проверок.

## Целевая структура и направление зависимостей

Сохранить корневой `app/`. Не выполнять перенос в `src/`.

Предпочтительная организация:

- `app/`: Expo Router adapters и layouts.
- `composition/`: только реально нужная сборка providers/startup и взаимодействия нескольких фич.
- `features/training/`: экраны и компоненты упражнений, training service, manager, session pools и правила подготовки заданий.
- `features/dialogues/`: список/сессия/ветка объяснения, assistant runtime hooks, API, cache и сценарии обработки ответов.
- `features/catalog/`: UI каталогов/тем и относящиеся к нему hooks.
- `features/account/`: вход, регистрация, подтверждение, onboarding, профиль и их операции.
- Общие независимые модули session, vocabulary/selection, progress, audio и transport: вынести в `shared/` лишь то, что действительно используется несколькими фичами. Для них разрешены узкие тематические подпапки; не создавать универсальный сервис на каждую функцию.
- `db/`, `mob-ui/`, assets, locales, scripts и конфигурацию сохранять в привычных местах, когда перенос не решает проблему зависимости.
- Общие визуальные компоненты остаются общими; training/dialogue/catalog-specific компоненты размещаются рядом со своей фичей после выделения ответственности.

Правила: `app/composition → features → shared/infra`. Одна фича не импортирует другую, включая типы. Связь dialogue → training проходит через существующий маршрут с IDs и независимые общие операции, а не импорт соседней фичи. Shared/DB/UI-kit не импортируют feature, screen или route. Чистые модели не импортируют React Native, Router, WatermelonDB runtime, UI metadata или глобальный UI store.

Не заводить одновременно `screens/` верхнего уровня и дублирующий слой экранов в фичах. Экраны живут внутри фич, а композиция появляется только при реальной сборке нескольких фич. Существующие небольшие barrel-файлы не переписывать массово, новых реэкспортов всего модуля не добавлять.

## Владельцы данных

| Данные | Основной владелец | Временное представление |
| --- | --- | --- |
| Слова, переводы, темы, каталоги, синонимы | Локальная WatermelonDB; обновления через явные vocabulary операции | Подготовленные данные нужных слов в words pool, обновляемые words service |
| Прогресс | WatermelonDB, progress service поверх persistence | Вычисленные coverage/remaining; не независимая копия score в нескольких stores |
| Выбранные каталоги/темы | Общий selection state, сохранение через существующие user settings keys | Snapshot условий при старте сессии |
| Training session | Training service и session store | Session ID, исходные word IDs, текущий шаг, допустимые training IDs, статус/ошибка |
| Training pool | Training session | Список незавершённых типов упражнений, согласованный с progress и исходным набором слов |
| Words pool | Words service для данных; training service для выбранных IDs/очереди | Не два сервиса, независимо заменяющих один массив целиком |
| Session/token lifecycle | Общий session owner, SecureStore и существующая users table | Тонкий consumer hook без повторного refresh на каждом mount |
| Диалоги | Серверные записи и существующий локальный cache/draft по user/session | Runtime текущего открытого диалога, без перезаписи текущего ответа запоздалой загрузкой |
| Sync/audio status | Один coordinator соответствующей операции | UI подписывается на status/progress; не запускает отдельную копию работы |

## Этап 1. Границы, доменные типы и проверки

1. Зафиксировать этот план и пользовательский `AGENTS.md`.
2. Отделить чистый справочник упражнений от UI metadata. Сохранить реальные IDs и различие `intro`, `type_word`, `type_translation`, серверных значений; не нормализовать их наугад.
3. Ввести import restrictions, совместимые с установленным Biome. Для графа зависимостей использовать минимальный Node/TypeScript AST script, если Biome не покрывает требования.
4. Проверять alias и relative imports, type-only импорты, реэкспорты и циклы. Не ограничиваться grep, который можно обойти относительным путём.
5. Добавить проверку в scripts/CI и при необходимости precommit, без изменения SDK/lockfile. Не запускать строгую проверку на промежуточной немигрированной части без прозрачного временного списка; итоговый allowlist не должен маскировать новые архитектурные нарушения.

Критерий: существующие тесты проходят; правила проверяют реальные запрещённые зависимости и не ломают допустимую композицию.

## Этап 2. Words service и Progress service

1. Вынести загрузку пар слово–перевод, синонимов, допустимых ответов и distractors из компонентов/контекста.
2. Разделить получение данных и политику выбора слов. Важные правила подбора не остаются в низкоуровневом words repository.
3. Выделить progress service: чтение по user/word/training, сохранение результата, вычисление покрытия и незавершённых упражнений.
4. Не сохранять результаты из отображающих компонентов напрямую. Существующий событийный context делегирует в сервис.
5. Обеспечить последовательность чтение/изменение результата и отсутствие дублирования при повторной обработке одного ответа; не блокировать намеренные повторные ответы следующего задания.

Критерий: тесты бизнес-правил запускаются без React Native; progress отделён по user/word/training; ошибка сохранения не превращается в успешное завершение; недостаток distractors не убирает основное задание.

## Этап 3. Единая training session и пулы

1. Выделить чистые операции над сессией: подготовка, список оставшихся тренировок, выбор следующего типа, выдача задания, применение результата и завершение.
2. Передавать условия явно: user, оба языка, каталоги/темы или word IDs, набор exercise IDs, режим сессии. Не определять бизнес-режим по pathname внутри сервиса.
3. Сохранять исходный набор подходящих word IDs на время сессии. Рабочая очередь меняется, знаменатель прогресса остаётся стабильным. Фоновое обновление слов не должно произвольно заменить этот набор.
4. Сохранить приоритеты диалоговых слов, личных/выбранных каталогов, вводного chunk и лимит 20 для mixed; standalone не получает этот лимит автоматически.
5. Mixed и standalone используют один training pool. При 100% упражнение удаляется; пустой пул означает `completed`. Состояния `loading`, `ready`, `empty`, `error`, `completed` различаются.
6. Уже завершённые упражнения исключаются при открытии. Недоступное аудио исключает listening с сохранением существующего поведения отдельного listening screen.
7. При завершении одиночной тренировки сохранить возможность продолжить повторение и перейти дальше через существующие UI actions. Продолжение запускает явную review-сессию того же упражнения; старые scores не сбрасываются, mixed не возвращает завершённые упражнения автоматически. Определить и проверить отдельное покрытие текущего review-прохода, иначе повторная сессия немедленно завершится из-за сохранённых scores.
8. Генерация session/step IDs защищает от late response после смены языка, пользователя, фильтров или выхода. Ответ привязан к тому заданию, на которое отвечал пользователь, а не к уже изменившемуся currentPairs.
9. Сохранение результата завершается до пересчёта пула и следующего выбора. Подписки/события не потребляют очередь дважды.

Критерий: тесты mixed и single используют одно ядро; проверены quick answer, failed review, пустой/полностью пройденный набор, matching, повторная доставка события, смена сессии во время async операции и явное повторение после 100%.

## Этап 4. Training manager, контекст и UI

1. Подключить новую сессию через `useTrainingManager` и узкие store selectors.
2. Оставить context интерфейсом событий/обратной связи; убрать из него запросы БД и собственную параллельную очередь.
3. Упростить TrainingAppWrapper: отображение выбранного упражнения, прогресса, состояний и действий. Подбор следующей темы/упражнения и чтение БД вынести.
4. Упражнения получают подготовленные данные и отправляют пользовательские действия. Локальные input/animation состояния сохраняются; бизнес-проверки правильности ответа становятся проверяемыми функциями.
5. Перенести feature-specific UI и обновить все потребители. Удалить старую очередь и старые функции подбора после переключения.
6. Разделить общий выбор каталогов/тем и session state; обновить каталог, defaults, intro и переход из диалога без изменения ключей хранения.

Критерий: компоненты тренировок не импортируют repositories/DB/API, UI не решает самостоятельно, какие слова попадут в сессию; существующие 15 regression-сценариев сохранены.

## Этап 5. Vocabulary, catalog и audio sync

1. Разделить `useVocabularySync` на сервис orchestration, persistence и audio download; hook связывает его с session и UI.
2. Явно описать локальную БД как источник тренировочных данных и обновление временных представлений. Устранить лишние копии vocabulary DTO там, где они не нужны; используемые UI поля перевести на наблюдаемые/согласованные данные.
3. Сохранить первичную блокирующую загрузку и неблокирующую фоновую синхронизацию, видимый прогресс, language checks, email verification guard и локальные audio paths.
4. Один coordinator объединяет одинаковые in-flight операции. Старый пользователь/язык не публикует результаты в новую сессию; записи БД также должны учитывать область операции.
5. Извлечь catalog data/subscriptions/default selection в hooks/services. Сохранить A1/A2, My Words, ручной deselect, язык, сохранённые темы и long press.
6. Сохранить audio fallback, загрузку отсутствующих файлов и поведение плеера; отделить файловые операции от отображающего контрола.
7. В документации перечислить фактические retry/conflict правила. Не заявлять durable outbox там, где его нет; не добавлять миграцию ради его появления в этой задаче.

Критерий: тесты cached/initial/offline/error, повторного запуска sync, смены языка/выхода, My Words defaults и частичной ошибки аудио; карточки каталога отображают свежий прогресс после результата.

## Этап 6. Диалоги и интеграция слов

1. Собрать dialogue API, types, cache и операции feature-local с корректным направлением зависимостей.
2. Вынести список диалогов, сценарии, detail, завершение и correction branch из маршрутов в feature screens/hooks.
3. Отделить adapter assistant runtime и обработку ответов от JSX; сохранить реальные runtime integration tests.
4. Сохранить draft persistence, message IDs/idempotency, порядок сообщений, cache fallback, offline состояние, retry и single-flight создания ветки.
5. Запоздалые результаты другого user/session/correction не заменяют открытый диалог; обновление props не затирает текущий ответ runtime.
6. Интеграция новых слов и progress идёт через общие vocabulary/progress операции; переход к mixed остаётся по существующему маршруту и IDs без импорта training feature.
7. Перенести приватные UI-компоненты рядом с feature; общие текстовые/визуальные примитивы не плодить.

Критерий: сохранены все correction regression tests; добавлены релевантные проверки detail/draft/смены user или session и ошибок интеграции слов. Клавиатура, выделения, перевод/подсказки и composer не меняют поведение.

## Этап 7. Session, auth, профиль и bootstrap

1. Один session owner восстанавливает токены и наблюдает пользователя. Повторные consumer hooks не запускают повторный refresh.
2. Auth/user persistence вынести в сервисы, формы и профиль используют feature hooks. Не менять endpoint contracts и refresh policy молча.
3. Bootstrap/layouts содержат providers/navigation и вызовы явных lifecycle hooks, а не процедуры upsert и загрузки vocabulary.
4. Logout сбрасывает session/selection/training/sync представления и отменяет публикацию устаревших результатов. Сохранить существующую политику хранения локальных данных.

Критерий: тесты shared hydration/refresh, error/retry, logout во время запроса, повторного mount, сохранения профиля и смены языка. В `app/` не остаётся самостоятельной бизнес-логики форм/БД.

## Этап 8. Общий код, удаление старых путей и документация

1. Проверить все маршруты и общие компоненты (report, language selectors, dev panel, progress indicators) на запрещённые зависимости и перенести конкретные операции в соответствующий hook/service.

3. Не менять хорошо разделённые UI-примитивы без конкретного нарушения. Производительность улучшать только при наблюдаемой причине; не добавлять memo/useCallback повсюду.
4. Добавить финальную карту модулей, владение данными, lifecycle сессии, sync/offline semantics и правила добавления нового упражнения.

Критерий: architecture check проверяет весь production-код, нет скрытых cross-feature импортов через старые aliases/barrels, каждый оставшийся крупный модуль имеет объяснимую единую ответственность.
