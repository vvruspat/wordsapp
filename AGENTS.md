# React Native + Expo: правила архитектуры и рефакторинга

Текущая структура приложения и владельцы данных описаны в [docs/architecture.md](docs/architecture.md), запуск и проверки — в [README.md](README.md).

## Назначение и приоритеты

Этот документ — адаптированная выжимка из Expo Skills, React Native Skills от Vercel и Bulletproof React, дополненная протоколом безопасного рефакторинга. Это не единый официальный стандарт этих проектов. Разделы помечены по происхождению. Проверено 19 октября 2026 года.

Применяй правила к фактическим версиям React, React Native и Expo в package.json и lockfile. Существующие требования продукта и явно заданная задача имеют приоритет над предлагаемой структурой. Не выполняй обновление стека как побочный эффект рефакторинга.

## 1. Архитектура модулей — адаптация Bulletproof React

- Группируй бизнес-код по фичам: компоненты, hooks, запросы, типы и утилиты одной фичи держи рядом.
- Создавай внутри фичи только необходимые каталоги. Пустые слои и одинаковые шаблоны для каждой фичи не нужны.
- Общий код размещай вне фич, когда он действительно используется несколькими модулями.
- Направление зависимостей: композиция приложения → фичи → общий код. Обратные зависимости запрещены.
- Не импортируй одну фичу из другой. Их взаимодействие организуй на уровне композиции приложения; общие понятия выделяй в независимый модуль только при реальной необходимости.
- Не создавай barrel-файлы, реэкспортирующие всё подряд: они усложняют зависимости и могут мешать сборке.
- Закрепляй ограничения импортов правилами линтера, совместимыми с текущей конфигурацией проекта.

Источник: https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md

## 2. Структура Expo — адаптация Expo Project Structure

- Рекомендация Expo по стартовой структуре предназначена для новых проектов. Не переносить существующее приложение в src/ только ради соответствия шаблону.
- В app/ или src/app/ держи маршруты, layouts и специальные файлы Expo Router. Обычные hooks, вспомогательные компоненты и бизнес-модули выноси за пределы каталога маршрутов.
- Крупный экран выноси в отдельный модуль. В маршруте оставляй подключение экрана и задачи маршрутизации.
- Приватные части экрана держи рядом с экраном; общий UI — в общем каталоге компонентов.
- Небольшие различия платформ оформляй через Platform; большие — через .ios/.android/.native/.web с согласованным интерфейсом.
- Серверные обработчики +api и серверные helpers отделяй от клиентского кода. Не импортируй серверные зависимости в приложение.
- Конфигурацию приложения, scripts и assets сохраняй в принятых проектом местах.

Источник: https://github.com/expo/skills/blob/main/plugins/expo/skills/expo-project-structure/SKILL.md

## 3. Контекст Expo — адаптация официальных инструкций

- Перед использованием API сверяй документацию с установленным Expo SDK.
- Для Expo-зависимостей используй npx expo install: версии должны соответствовать SDK.
- Выбирай нужную инструкцию Expo по задаче: Router, data fetching, UI, animation, native modules, upgrade или EAS.
- Учитывай ограничения Expo Go и development build при проверке нативных возможностей.
- Используй Expo CLI и актуальную документацию как источник истины при расхождении с общими советами модели.

Источники:
- https://docs.expo.dev/agents/
- https://github.com/expo/skills

## 4. Корректность и производительность — адаптация Vercel React Native Skills

- Текст рендери внутри Text. Для условного JSX используй явный boolean или тернарный оператор; не допускай попадания 0 в View через &&.
- Для длинных списков используй виртуализацию; строки делай лёгкими, изображения — оптимизированными. Стабилизируй props и callbacks там, где это помогает переиспользованию строк.
- Не обновляй React state на каждом кадре прокрутки. Для анимаций и жестов используй подходящие нативные механизмы/Reanimated.
- Где возможно, анимируй transform и opacity вместо свойств layout.
- Храни первичные данные, а производные значения вычисляй. При обновлении на основе предыдущего состояния используй функциональный updater.
- Для навигации предпочитай нативные навигаторы; учитывай safe area и поведение платформы.
- Используй компоненты дизайн-системы вместо создания очередной версии одинакового контрола.
- В монорепозитории устанавливай нативные зависимости в пакет приложения и согласовывай их версии.

Эти рекомендации не разрешают массовую замену библиотек. Детали API, React Compiler и Reanimated проверяй по версиям проекта. Оптимизации подтверждай измерением либо конкретной проблемой.

Источник: https://github.com/vercel-labs/agent-skills/blob/main/skills/react-native-skills/AGENTS.md

## 5. Данные и границы ответственности — дополнительные правила этой сборки

Следующие пункты — практическое дополнение для рефакторинга, а не дословные требования перечисленных источников.

- Для каждого набора данных определи владельца: компонент, feature-store, серверный cache или локальная БД.
- Не копируй одни и те же данные между несколькими stores без описанного механизма согласования.
- Компонент отвечает за отображение и пользовательские события. Побочные эффекты и операции с данными размещай в подходящих hooks или сервисах.
- Чистые бизнес-правила должны проверяться без запуска React Native. Не привязывай их к навигации и UI.
- Не добавляй repository/use-case/interface для каждой функции автоматически. Дополнительный слой должен иметь конкретную причину.
- При offline-first архитектуре документируй источник истины, очередь изменений, повторные попытки и конфликты. Не подменяй существующую синхронизацию обычным HTTP-cache.
- Сохраняй отмену запросов, очистку подписок, обработку ошибок и предотвращение повторных операций.
- Не скрывай ошибки пустым catch и не подменяй неуспешную операцию фиктивным успехом.

## 6. Протокол рефакторинга — дополнительные правила этой сборки

### Перед изменениями

1. Прочитай локальные инструкции, package.json, lockfile, tsconfig, настройки линтера и scripts.
2. Определи маршрутизацию, UI-kit, управление состоянием, HTTP-слой, БД и синхронизацию.
3. Зафиксируй исходное состояние проверок. Отдели существующие ошибки от новых.
4. Составь список конкретных нарушений: файл, зависимость, последствие и предлагаемое исправление.
5. Выбери небольшую законченную область изменения. Не начинай массовый перенос всего проекта.

### Во время изменений

- Сохраняй поведение, внешний вид, доступность, маршруты и контракты данных, если задача явно не требует другого.
- Сначала отделяй ответственность, затем перемещай код. Само переименование каталога не считается архитектурным улучшением.
- Не совмещай структурные изменения с обновлением SDK, заменой state-manager или изменением дизайна.
- Не меняй схему БД, ключи хранения, формат persisted state и deep links без отдельного плана совместимости.
- Сохраняй публичные интерфейсы либо обновляй все известные места использования в том же шаге.
- Не подавляй ошибки через any, ts-ignore, отключение линтера или удаление проверок.
- Удаляй старый код после переключения потребителей и проверки ссылок.
- Соблюдай существующие соглашения об именах и экспортах, если их изменение не входит в задачу.

### Проверка результата

- Запусти доступные typecheck, lint и относящиеся к изменению тесты через scripts проекта.
- Для изменения бизнес-логики или исправления ошибки добавь проверку наблюдаемого поведения. Не пиши тест только ради новой структуры файлов.
- Для изменения UI проверь затронутый сценарий на целевых платформах; включи loading, empty, error и offline, если применимо.
- При изменении нативных зависимостей или Expo-конфигурации выполни npx expo-doctor; при необходимости проверь development build.
- Проверь циклы и запрещённые импорты существующим инструментом проекта. Если его нет, предложи минимальный способ контроля.
- В отчёте укажи изменения, выполненные проверки, оставшиеся ошибки и то, что не удалось проверить. Не объявляй приложение проверенным на устройстве, если запускался только TypeScript.

## 7. Предлагаемая структура при явно выбранном feature-подходе

Это сочетание принципов выше, а не обязательное дерево Expo. Существующее приложение мигрировать к нему только в рамках согласованной задачи.

```text
src/
  app/                 Expo Router: маршруты и layouts
  screens/             композиция экранов из фич
  features/
    feature-name/
      components/      UI этой фичи
      hooks/           React-интеграция
      api/             операции с сервером
      model/           состояние и бизнес-правила
  components/          общий UI и дизайн-система
  hooks/               общие hooks
  lib/                 настроенные клиенты и инфраструктура
  utils/               общие чистые функции
  server/              только при наличии серверной части Expo
```

Не создавай одновременно screens/ и отдельный слой экранов внутри фич без объяснимой необходимости. Каталоги в примере добавляются по мере появления кода.

## 8. Как начать работу с этим документом

Сначала проведи аудит текущего проекта по этим правилам. Представь нарушения с примерами и приоритетами. Выдели применимые правила и несовпадения с текущим стеком. Затем предложи последовательность небольших изменений с критериями проверки. Рефакторинг выполняй в пределах порученной задачи; не считай этот документ разрешением на переписывание приложения.
